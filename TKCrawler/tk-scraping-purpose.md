# TK 数据抓取目的说明（为什么要采这些数据）

> 日期：2026-10-07
> 配套文档：`tk-selection-data-schema.md`（采什么）、`tk-crawler-github-references.md`（怎么采/借什么）
> 合规基线：只抓公开数据 + 用户授权会话，只读不写，不做池化绕过。

---

## 1. 一句话目的

**把 TikTok 上"什么好卖、谁在推、推得怎么样"变成可量化、可追踪、可复盘的结构化数据，替代人工刷广场拍脑袋选品，把选品决策从经验驱动变成数据驱动。**

## 2. 数据服务于一条选品决策链

```text
发现（什么在涨）→ 初筛（能不能做）→ 深筛（做有没有得赚）→ 测试（内容行不行）→ 放大（要不要压货）
```

每个环节由不同数据驱动，**每个字段都有明确决策用途，没有"先存了再说"的字段**：

| 数据维度 | 回答的问题 | 直接支撑的决策 |
|---------|-----------|--------------|
| 商品（P0） | 什么在卖、卖多少、涨多快 | 选品 Pool 榜单、飙升品识别 |
| 视频/内容（P0） | 靠什么素材卖出去的 | 素材模板库、3 秒钩子测试、内容效率评估 |
| 达人（P0 简版） | 谁在推、推得动吗 | 达人建联名单、分销策略 |
| 话题/标签（P1） | 需求处于什么热度阶段 | 入场/离场时机判断 |
| 竞品店铺（P1） | 对手怎么打 | 定价对标、打法分析 |
| 供应链（P1） | 货从哪来、利润够不够 | 采购报价、毛利测算、快返能力验证 |
| 外部验证（P1） | 需求是真趋势还是内容幻觉 | 最终"做/不做"的交叉确认 |

## 3. 核心设计：快照差分

单次抓取只能看到"存量"（当前销量、当前视频数）。**真正值钱的是"增量"——增速**。所以对同一商品 ID 做周期快照（2-3 天/次），差分出 `gmv_growth_7d/30d`，才能在爆款生命周期（2-8 周）的前半段发现它，而不是接盘。这是调度系统必须支持周期重抓的原因。

## 4. 数据的两个消费方

1. **选品决策（人）**：漏斗各环节的筛选报告与评分排名，最终由人拍板"做/不做/压多少货"。
2. **内容与投放（分析层）**：派生指标（内容效率 = GMV÷视频数、达人渗透率、饱和度指数等）用于反推"素材怎么拍、达人怎么配、价格怎么定"。数据入库后计算，不采集。

## 5. 边界与诚实性约束

- **估算不当精确值**：前台销量是区间值、第三方 GMV 是估算，所有分析输出必须标注数据来源与置信级别；估算字段只用于排序和筛选，不作为最终财务决策依据。
- **过时即弃**：TK 爆款周期短，数据只保留决策窗口内的价值，快照过期数据不参与当前排名。
- **风控优先于数据完整性**：软冷却/空 body/WAF 即停，宁可当天数据缺失，不冒账号风险补抓。
