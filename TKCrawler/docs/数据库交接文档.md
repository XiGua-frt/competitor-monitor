## 2. 核心设计：每日快照模型（最重要，先读这段）

整个数据库是**快照型（snapshot-per-day）设计**，不是实时状态表：

- 共 **4 张快照表**：`product_snapshots` / `video_snapshots` / `creator_snapshots` / `hashtag_snapshots`
- 每张表主键统一为 **`(实体ID, snapshot_date)`**——同一实体每天一条快照
- **同一天重复写入走 upsert**（冲突目标 = 主键两列），不会产生重复行。见 `src/database/snapshot_engine.py` 的 `SnapshotDiffEngine.save_snapshot`
- **增速字段不存在于表中**：`gmv_growth_7d/30d`、`views_growth_7d` 等均由两次快照**差分计算**得出（`calculate_growth` / `compute_growth_values`），不是物理列。任何规划文档里出现的 growth 字段都是派生值
- 除零语义遵循 SQL `NULLIF` 约定：任一输入缺失 → 增速为 NULL；`past == 0` → 增速率为 NULL、绝对差值仍返回

**为什么这么设计**：TikTok 前台只给"当前值"，销量区间、GMV 都要靠每日快照差分才能算出趋势——这是选品系统最值钱的数据。

### 写入接口（采集层统一入口）

```python
# src/database/snapshot_engine.py — SnapshotDiffEngine
save_snapshot(data: dict, table: str) -> bool
    # table 合法取值（白名单）：'product_snapshots' / 'video_snapshots' /
    # 'creator_snapshots' / 'hashtag_snapshots'
calculate_growth(product_id: str, days: int) -> dict
get_latest_snapshot(product_id: str) -> dict
```

## 3. 表结构详单

### 3.1 `product_snapshots` — 商品快照（15 业务字段 + 2 主键 + 1 审计）

⚠️ **PostgreSQL RANGE 分区表**（按 `snapshot_date` 逐月分区），分区 DDL 在迁移脚本 `001_initial_schema.py` 中用 raw SQL 管理：

- 初始分区：2026-01 ~ 2026-12 逐月 + `product_snapshots_default` 兜底
- 越界日期数据写入 default 分区；新月份用 `connection.ensure_month_partition(target_date)` 补建（`IF NOT EXISTS`，幂等）
- 分区命名：`product_snapshots_YYYYMM`，边界 `[月初, 次月初)`
- 分区表上的索引建在父表，PG 自动传播到所有分区

| 字段 | 类型 | 约束 | 来源/口径 | 说明 |
|------|------|------|-----------|------|
| product_id | VARCHAR(50) | **PK** | 商品 URL 提取 | 商品唯一 ID |
| snapshot_date | DATE | **PK** | 系统生成（采集日） | 快照日期，分区键 |
| title | VARCHAR(500) | 可空 | 页面采集 | 商品标题 |
| category_l1 | VARCHAR(100) | 可空 | 页面面包屑 | 一级类目 |
| category_l2 | VARCHAR(100) | 可空 | 页面面包屑 | 二级类目 |
| category_l3 | VARCHAR(100) | 可空 | 页面面包屑 | 三级类目 |
| price_current | NUMERIC(10,2) | 可空 | 页面采集（USD） | 当前售价 |
| price_original | NUMERIC(10,2) | 可空 | 页面采集 | 划线原价 |
| sales_30d | INTEGER | 可空 | 页面 + 解析 | 近 30 天销量，**区间取中位数**（`"500-1k"`→750，`"10k+"`→10000，见 `ShopProductScraper.parse_sales_range`） |
| gmv_30d_est | NUMERIC(15,2) | 可空 | **派生计算** = price_current × sales_30d（`parsers/product_parser.py`） | 30 天 GMV 估算，非页面直接提取 |
| listed_date | DATE | 可空 | 页面采集 | 上架日期 |
| shop_id | VARCHAR(50) | 可空 | 页面采集 | 店铺 ID（聚合键） |
| shop_name | VARCHAR(200) | 可空 | 页面采集 | 店铺名 |
| creator_count | INTEGER | 可空 | 页面"达人带货"模块 | 关联达人数 |
| video_count_7d | INTEGER | 可空 | 页面采集 | 近 7 天关联视频数 |
| review_count | INTEGER | 可空 | 页面采集 | 评论数 |
| rating | NUMERIC(3,2) | 可空 | 页面采集 | 评分（0-5） |
| created_at | TIMESTAMP | 非空, `DEFAULT NOW()` | 系统生成 | 入库时间审计 |

索引：`idx_product_snapshots_date(snapshot_date)`、`idx_product_snapshots_shop(shop_id)`、`idx_product_snapshots_category(category_l1, category_l2)`

### 3.2 `video_snapshots` — 视频快照（普通表）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| video_id | VARCHAR(50) | **PK** | 视频 ID |
| snapshot_date | DATE | **PK** | 快照日期 |
| product_id | VARCHAR(50) | 可空 | 挂车商品 ID（关联 product_snapshots） |
| author_id | VARCHAR(50) | 可空 | 作者 ID（关联 creator_snapshots） |
| publish_time | TIMESTAMP | 可空 | 视频发布时间 |
| views | INTEGER | 可空 | 播放量 |
| likes | INTEGER | 可空 | 点赞 |
| comments | INTEGER | 可空 | 评论数 |
| shares | INTEGER | 可空 | 分享数 |
| duration | INTEGER | 可空 | 时长（秒） |
| is_paid | BOOLEAN | 可空 | 是否投流（Spark Ads 标识） |
| created_at | TIMESTAMP | 非空 | 审计 |

索引：`idx_video_snapshots_product(product_id, snapshot_date)`

### 3.3 `creator_snapshots` — 达人快照（普通表）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| creator_id | VARCHAR(50) | **PK** | 达人 ID |
| snapshot_date | DATE | **PK** | 快照日期 |
| nickname | VARCHAR(200) | 可空 | 昵称 |
| follower_count | INTEGER | 可空 | 粉丝数 |
| avg_views_30d | INTEGER | 可空 | 近 30 天视频中位播放（防僵尸粉） |
| category_tags | VARCHAR(500) | 可空 | 带货类目标签，**逗号分隔存储**（如 `kitchen,home,gadgets`） |
| product_count | INTEGER | 可空 | 橱窗商品数 |
| created_at | TIMESTAMP | 非空 | 审计 |

索引：`idx_creator_snapshots_followers(follower_count)`

### 3.4 `hashtag_snapshots` — 话题快照（普通表）

| 字段 | 类型 | 约束 | 说明 |
|------|------|------|------|
| tag_name | VARCHAR(200) | **PK** | 话题名（不含 #，如 `tiktokmademebuyit`） |
| snapshot_date | DATE | **PK** | 快照日期 |
| views_total | INTEGER | 可空 | 话题总播放量 |
| created_at | TIMESTAMP | 非空 | 审计 |

索引：`idx_hashtag_snapshots_date(snapshot_date)`

> ⚠️ 注意：`views_total` 当前是 INTEGER，头部话题播放量可达百亿级（如 12,500,000,000），接近 int32 上限（2,147,483,647）会**溢出**。PG 的 INTEGER 是 4 字节——接手方如存头部话题建议改 BIGINT。

### 3.5 表间关系（逻辑外键，无物理 FK 约束）

```
product_snapshots (product_id) ←── video_snapshots.product_id
creator_snapshots (creator_id) ←── video_snapshots.author_id
```

均为**逻辑关联**，建表时未设 FOREIGN KEY 约束（快照设计 + 采集先到先入，允许悬挂引用）。

## 4. 派生指标（不落表，查询时计算）

| 指标 | 公式 | 用途 |
|------|------|------|
| content_efficiency 内容效率 | `gmv_30d_est ÷ video_count_7d` | 单条内容产出 |
| creator_penetration 达人渗透率 | `creator_count ÷ sales_30d` | 达人驱动 vs 自播驱动 |
| saturation_index 饱和度指数 | `(creator_count × video_count_7d) ÷ gmv_30d_est` | 竞争拥挤度，越高越卷 |
| surge_coefficient 飙升系数 | `gmv_growth_30d ÷ 类目平均增速` | 识别飙升品（Pool 榜单核心排序） |
| gmv_growth / growth_rate | 两次快照 GMV 差分（`compute_growth_values`） | 绝对增量 + 增长率（小数，0.25 = +25%） |

实现注意：所有分母用 `NULLIF(x, 0)` 防除零。⚠️ `src/metrics/` 目录目前为空，`MetricsCalculator` 尚未落地——以上公式来自任务卡设计，接入方如需使用需自行实现或等待本侧交付。

## 5. 数据质量与口径约定（交接必读）

1. **销量是区间中位数**：前台只给 `"500-1k"` 这类区间，入库为推算值（750），不是精确销量。所有分析输出须标注"估算"。
2. **GMV 是估算值**：`gmv_30d_est = price_current × sales_30d`，两重估算叠加，禁止当精确值做最终决策。
3. **字段可空是常态**：反爬、页面改版都会导致单次采集部分字段缺失，查询逻辑必须容忍 NULL。
4. **增速靠差分**：单独一天的快照没有趋势信息；至少两个 `snapshot_date` 才能计算 growth。
5. **采集节奏**：商品快照建议每 2-3 天一次（系统调度任务如 `scrape_shop_products` / `scrape_videos` 按间隔轮询）。

## 6. 非数据库数据文件（data/ 目录格式）

| 文件 | 格式 | 说明 | 交接处理 |
|------|------|------|----------|
| `data/scheduler_state.json` | JSON，顶层为 `{task_id_or_name: {task_id, created_at, task_name, priority, status, updated_at, attempts?, interval_seconds?}}` | 调度器任务状态持久化（Redis 的落盘镜像） | 运行时状态，**不需要**迁移，新环境自动重建 |
| `data/session.json` / `data/sessions/*.json` | JSON（cookie / msToken / device_id 等会话材料） | 爬虫登录态 | ⚠️ **敏感，严禁随交接文档外发**，不迁移 |
| `logs/` / `exports/` | 日志与导出产物 | — | 不迁移 |
